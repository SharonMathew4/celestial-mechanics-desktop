Executive Summary

A concise overview of the project, its goals, and its achievements

The Celestial Mechanics Desktop Engine is a native, high-performance gravitational N-body simulation platform built for real-time execution on Windows desktop hardware. It bridges rigorous astrophysical science with interactive, visually stunning rendering — enabling users to simulate, observe, and analyze the gravitational dynamics of stellar systems, galaxy formation, planetary orbits, and exotic phenomena such as black-hole mergers and neutron star collisions.

The project unifies a C++20/CUDA native physics engine (exposed via a pure C P/Invoke API) with a C#/.NET 8 application layer backed by OpenGL rendering through Silk.NET. Problem Statement

Why does this project exist? What problems does it solve?

2.1 The N-Body Computational Challenge

Simulating the gravitational interaction of N bodies is one of the oldest and most computationally demanding problems in computational physics. Every body exerts a gravitational force on every other — giving rise to N(N−1)/2 pairwise interactions per timestep. For N = 10,000 bodies, this is ~50 million force evaluations per step. At 60 fps, that is 3 billion per second — far beyond what naive CPU code can handle.

F_ij = -G · m_i · m_j · (r_i − r_j) / |r_i − r_j|³ ← Newton's law of gravitation (pairwise, direct sum) a_i = Σ_{j≠i} G · m_j · (r_j − r_i) / (|r_j − r_i|² + ε²)^(3/2) ← Softened acceleration on body i (sum over all N−1 others) Naive complexity: O(N²) → 10k bodies = 50M evals/step Barnes-Hut: O(N log N) → 10k bodies = ~130k evals/step

Section 04

Complete Physics Model

Every physical law implemented in the engine — from first principles to code

4.1 Newtonian Gravity & the N-Body Problem

The foundation of the simulation is Newton's law of universal gravitation. Every pair of bodies attracts each other with a force proportional to the product of their masses and inversely proportional to the square of the distance between them:

F⃗ᵢⱼ = G · mᵢ · mⱼ · (r⃗ⱼ − r⃗ᵢ) / |r⃗ⱼ − r⃗ᵢ|³ where G = 6.674 × 10⁻¹¹ N·m²·kg⁻² (or G = 1 in N-body code units) r⃗ᵢ = position vector of body i, mᵢ = mass of body i Net acceleration on body i from all others: a⃗ᵢ = Σⱼ≠ᵢ [ G · mⱼ · (r⃗ⱼ − r⃗ᵢ) / |r⃗ⱼ − r⃗ᵢ|³ ]

This is a coupled system of 6N ordinary differential equations (3 positions + 3 velocities per body). For N > 2, no closed-form analytic solution exists — numerical integration is mandatory. The engine solves this system at every simulation timestep.

4.2 Numerical Integration Methods

Choosing the right integrator is critical for long-term accuracy. The engine implements three, each with different error characteristics:

Velocity Verlet (KDK)

Symplectic · 2nd Order

Kick-Drift-Kick leapfrog scheme. Exactly solves a nearby Hamiltonian H̃ = H + O(dt²) — energy error oscillates around zero but never drifts secularly. Phase space volume is preserved exactly.

v(t+½dt) = v(t) + ½dt·a(t) ← Half-Kick x(t+dt) = x(t) + dt·v(t+½dt) ← Drift a(t+dt) = f(x(t+dt)) ← Forces v(t+dt) = v(t+½dt) + ½dt·a(t+dt) ← Half-Kick
  • Default integrator for all production runs
  • Excellent energy conservation over billions of steps
  • Used in all 8 compute mode paths

Yoshida 4th-Order

Symplectic · 4th Order

Forest-Ruth composition of three Leapfrog substeps with special coefficients. O(dt⁴) global error — superior to Verlet for high-accuracy orbital mechanics. Uses negative middle timestep (runs simulation backwards briefly).

w₁ = 1/(2 − ∛2) ≈ +1.3512 w₀ = −∛2/(2 − ∛2) ≈ −1.7024 Substep 1: KDK with w₁·dt Substep 2: KDK with w₀·dt ← NEGATIVE Substep 3: KDK with w₁·dt Check: 2w₁ + w₀ = 1 ✓
  • 3× force evaluations per step vs Verlet
  • Recommended for star cluster long-term evolution

Runge-Kutta 4 (RK4)

Non-Symplectic · 4th Order

4 force evaluations per step (k₁–k₄). O(dt⁵) local error, O(dt⁴) global. Not symplectic — exhibits secular energy drift over long simulations. Best for short-term high-accuracy trajectory comparisons.

k₁ = f(t, y) k₂ = f(t+½dt, y+½dt·k₁) k₃ = f(t+½dt, y+½dt·k₂) k₄ = f(t+dt, y+dt·k₃) y(t+dt) = y(t) + (dt/6)(k₁+2k₂+2k₃+k₄)
  • Not recommended for >10⁶ step runs
  • Good for validation vs Verlet

4.3 Barnes-Hut O(N log N) Algorithm

The naive O(N²) direct summation becomes prohibitive beyond a few thousand bodies. The Barnes-Hut algorithm (1986) approximates the gravitational force using a hierarchical octree (3D spatial tree), reducing complexity to O(N log N).

Core Idea: If a group of bodies is sufficiently far away, treat the entire group as a single point mass located at the group's center of mass.

Opening Angle Criterion (θ — controls accuracy vs speed): If (2·s)² < θ² · d² → use monopole approximation where s = node half-size, d = distance from body to node COM Monopole force (same as direct, but from aggregate mass M_node): a⃗ᵢ += −M_node · (r⃗ᵢ − COM_node) / (|r⃗ᵢ − COM_node|² + ε²)^(3/2) θ accuracy table: θ = 0.0 → O(N²) exact θ = 0.5 → ~0.1% error (default) θ = 1.0 → ~1% error θ = 1.5 → ~5% error (visual only) Engine enforces θ_min = 0.2 to prevent degenerate O(N²) behavior

4.4 Gravitational Softening

In reality, point masses at zero separation would produce infinite forces. In simulation, bodies that approach closely would experience unphysical divergence. Gravitational softening introduces a length scale ε that regularizes the force at short range:

a⃗ᵢⱼ = G·mⱼ·(r⃗ⱼ−r⃗ᵢ) / (|r⃗ⱼ−r⃗ᵢ|² + ε²)^(3/2) Three softening modes implemented: 1. Global: Single ε for all body pairs (fast, simple) 2. PerBodyType: ε_ij = mean(ε_type[i], ε_type[j]) (lookup table) 3. Adaptive: ε_i = scale · ∛(mᵢ) (mass-proportional per body)

4.5 Post-Newtonian (1PN) Relativistic Corrections

For compact objects (neutron stars, black holes), purely Newtonian gravity is insufficient — General Relativity produces measurable orbital precession (Mercury's perihelion, binary pulsar decay). The engine implements first Post-Newtonian (1PN) corrections via the Einstein-Infeld-Hoffmann (EIH) equations, which are accurate to order (v/c)² relative to Newtonian gravity:

a⃗ᵢ^(1PN) = Σⱼ≠ᵢ [ Gₘⱼ/rᵢⱼ³ · { rᵢⱼ (−v²ᵢ − 2v²ⱼ + 4v⃗ᵢ·v⃗ⱼ + 3/2(n̂ᵢⱼ·v⃗ⱼ)² + 4Gₘᵢ/rᵢⱼ + 5Gₘⱼ/2rᵢⱼ) + v̇ⱼ(4v⃗ᵢ·n̂ᵢⱼ − 3v⃗ⱼ·n̂ᵢⱼ) } ] / c² Applied as: a⃗_total = a⃗_Newtonian + a⃗^(1PN) Implemented as a Decorator over any force backend (PostNewtonianBackend.cs) Key effects: orbital precession, gravitational time dilation corrections

4.6 Collision Physics

The engine implements a three-stage collision pipeline — Detection → Resolution → Compaction — with four physically distinct resolution modes:

IgnoreBodies pass through each otherEnergy, Momentum (trivial)Test / ghost particles

Merge conservation laws (verified post-resolution to 1e-10): M_survivor = mₐ + m_b v⃗_merged = (mₐv⃗ₐ + m_b·v⃗_b) / M_survivor r⃗_merged = (mₐr⃗ₐ + m_b·r⃗_b) / M_survivor ← COM position r_merged = ∛(rₐ³ + r_b³) ← Volume-conserving radius Safeguards: max 64 merges/frame, max 2 merges/body

4.7 Adaptive Timestep Control

Using a fixed timestep dt risks missing fast close encounters or wasting computation during calm phases. The adaptive timestep dynamically scales dt based on the maximum acceleration in the system:

dt_next = η · √(ε / a_max) where η = accuracy parameter (default 0.02), ε = softening length a_max = maximum acceleration across all active bodies Clamped to [dt_min, dt_max] to prevent runaway shrinkage or growth Applied between Leapfrog steps (preserves per-step symplecticity)

4.8 Energy Conservation & Diagnostics

The EnergyTracker computes a full energy snapshot every step (or on demand), monitoring conservation to detect integration errors or numerical instabilities:

Kinetic Energy: KE = ½ Σᵢ mᵢ|v⃗ᵢ|² Potential Energy: PE = −G Σᵢ Σⱼ>ᵢ mᵢmⱼ / |r⃗ᵢ−r⃗ⱼ| (O(N²) or O(N log N) via BH) Total Energy: E = KE + PE ← should be ~constant (Verlet: oscillates, no drift) Linear Momentum: P⃗ = Σᵢ mᵢv⃗ᵢ ← exactly conserved by symmetric force law Angular Momentum: L⃗ = Σᵢ mᵢ(r⃗ᵢ × v⃗ᵢ) ← conserved in isolated system Virial Ratio: K = −KE / PE ← K ≈ 0.5 for virialized system Rolling average window: 300 samples ← suppresses per-step oscillation

4.9 Gravitational Wave Emission

Inspiraling compact binary systems (black holes, neutron stars) radiate energy as gravitational waves, causing orbital decay. The engine computes gravitational wave strain using the quadrupole formula:

h_+ = (2G/c⁴r) · (Ï_xx − Ï_yy) ← "plus" polarization h_× = (4G/c⁴r) · Ï_xy ← "cross" polarization where Ï_ij = second time derivative of quadrupole moment tensor Ï_ij = Σₖ mₖ(2ṙₖᵢṙₖⱼ + rₖᵢr̈ₖⱼ + r̈ₖᵢrₖⱼ) Power radiated: dE/dt = −G/(5c⁵) · Ï̈ᵢⱼ Ï̈ᵢⱼ (Peters formula) Implemented: GravitationalWaveAnalyzer.cs + IGravitationalWaveModel interface Waveform buffer: WaveformBuffer.cs (time-series h+(t), h×(t) for visualization)

5.5 Determinism System

Scientific reproducibility demands that identical initial conditions produce identical results across runs. The engine achieves bit-exact determinism in 6 of 8 modes through:

  • Fixed Dispatch Order: All iterations use fixed index order. No work-stealing, no dynamic scheduling
  • GPU Pipeline Drain: cudaDeviceSynchronize() called after each kernel when deterministic mode is active
  • CUDA Cache Config: cudaFuncCachePreferL1 disables auto-tuning that varies between runs
  • SplitMix64 PRNG: Hash function parameterized by (seed, step_number, channel) — not a sequential generator
  • Collision Pair Sort: Pairs sorted by (min(a,b), max(a,b)) for canonical ordering before resolution
  • Kahan GPU Reduction: Compensated summation on host eliminates floating-point ordering variance
⚡
GPU Barnes-Hut Non-Determinism

GPU_BarnesHut mode is non-deterministic due to atomicAdd in the Morton radix sort scatter phase. When two threads map to the same radix bucket, resolution order is non-deterministic (GPU warp scheduling). The inter-run variance is <0.01% RMS — far below the ~1% Barnes-Hut approximation error itself. Physically inconsequential.

8.2 Key Optimization Techniques

  • Structure-of-Arrays (SoA) layout: 18 parallel arrays (PosX[], PosY[], PosZ[], ...) for cache-friendly sequential reads vs. Array-of-Structures
  • OctreePool pre-allocation: Pool capacity = 4N + 64 nodes (~148 bytes/node). Allocated once, Reset() called each step — zero heap allocation in hot path
  • GPU Tiled Gravity Kernel: TILE_SIZE×TILE_SIZE threads cooperatively load positions into shared memory before computing forces, reducing global memory bandwidth by ~√N
  • Morton Z-order Curve: Sort particles by 30-bit 3D Morton code before GPU octree build. Spatially nearby particles are memory-adjacent → cache efficiency
  • Double-buffered GPU Pipeline: Async H2D/D2H transfers overlap with CPU-side collision resolution — GPU never idle waiting for CPU
  • SIMD Force Computation: System.Numerics.Vector<double> processes 4 bodies per instruction on AVX2 hardware (1.5–3× speedup over scalar C#)
  • Job System Parallel BH: Force traversal parallelized over body index via lock-free MPMC work queue (64-worker thread pool). Tree is read-only post-build — no locks needed
  • Warp Shuffle Reductions: GPU energy reduction uses warp shuffle (__shfl_down_sync) instead of shared memory atomics — 4× faster than atomic reduction

8.3 Memory Architecture

GPU Memory Budget (256 MB GpuPool): SoA arrays (15 × N × 8 bytes): 50k bodies = 6 MB Octree nodes (~148 bytes × 4N): 50k bodies = 29.6 MB Morton keys (4 bytes × N): 50k bodies = 0.2 MB Prefix-scan work buffer: ~1 MB Total GPU working set: ~37 MB for 50k bodies (well within 256 MB pool) CPU Memory (SoA, 50k bodies): 18 arrays × 50,000 × 8 bytes = 7.2 MB ← trivial for modern systems

9.2 Physics Validation Benchmarks

  • Two-body circular orbit: Verify that KE, PE, total E, and angular momentum remain constant to 10⁻⁶ relative precision over 10⁶ steps with Verlet integrator
  • Kepler's 3rd Law: For two-body bound orbit, verify T² ∝ a³ (orbital period² vs semi-major axis³) to within 0.1%
  • Mercury Precession (1PN test): With 1PN correction enabled, verify 43 arcseconds/century perihelion advance for Mercury-like orbit around a solar-mass body
  • Barnes-Hut force accuracy: Compare BH forces (θ=0.5) to exact O(N²) forces for 100-body random config — RMS error < 0.1%
  • Determinism test: Run 100 steps twice with same seed — all positions identical to the last double-precision bit (EXPECT_DOUBLE_EQ passes)
  • Collision conservation: After merge, verify |mass_error| < 10⁻¹⁰ and |momentum_error| < 10⁻¹⁰
  • 50k body energy drift: GPU BH mode, 10,000 steps — total energy drift < 1% (dominated by BH approximation, not integrator error)

Validation Philosophy

Every approximation in the engine has a documented error bound. The test suite verifies that the implementation matches those bounds. Physics is not "approximately right" — it is either within specification or the test fails.

Conclusion & Vision

What has been built, what it means, and where it goes

10.1 What Has Been Achieved

The Celestial Mechanics Desktop Engine represents a significant engineering achievement: a production-quality, scientifically rigorous N-body simulation platform running in real time on consumer hardware. In approximately 21 development phases, the project has delivered:

  • A five-layer software architecture from core constants to OpenGL rendering, with zero circular dependencies
  • Four compute backends covering CPU and GPU, brute-force and tree-based algorithms
  • Three numerical integrators with different accuracy and conservation properties
  • Post-Newtonian relativistic corrections enabling compact binary system simulation
  • Gravitational wave emission modeling using the quadrupole formula
  • A complete three-stage collision pipeline with GPU-resident merge-and-compact
  • Bit-exact deterministic reproducibility in 6 of 8 execution modes
  • 100+ automated physics validation tests
  • Real-time rendering with gravitational lensing, accretion disk glow, and nebula post-processing

10.2 Scientific Significance

The physics implemented in this engine spans multiple decades of astrophysics research — from Newton's 17th century law of gravitation, to Yoshida's 1990 symplectic coefficients, to modern GPU-accelerated octree algorithms. By making these methods accessible interactively on a desktop, the project democratizes access to tools previously requiring HPC cluster time.
